Processes.Process

A running program. Its standard output and standard error come back through `Output`, and what is written to `Input` reaches its standard input.

Processes.Process.Waiting

Is there output to be had without waiting for it? A program with an event loop asks this rather than reading, so that a quiet child does not stop it answering its keys.

Processes.Process.WriteLine

A line, ended the way a Unix program expects one: a single newline. Streams.Writer.Ln writes a carriage return before it -- the Oberon convention -- and a child that reads lines would take that as part of the line. Programs that want the other thing can still write it through `Input`.

Processes.Start

Start `program`, looked up on the PATH as a shell would look it up, with `arguments` -- of which the first is the name the program sees as its own, as usual.

NIL when the start itself failed. A name that is not a program may come back either way, and that is the C library's choice, not ours: some report it here, and some let the child be made and have it fail to become the program, which is an exit code of 127 -- the number a shell uses for the same thing. A caller that must know should look at both.

Syntax

PROCEDURE Start* (CONST program: ARRAY OF CHAR; arguments: Strings.StringArray): Process

Processes.StartAttached

Start a program that takes the terminal over -- an editor, a pager -- rather than one that is spoken to. It inherits this program's own input and output, so there is nothing to read and nothing to write: what it does, it does to the screen. A full-screen program should give the terminal back first (Terminal.Close) and take it again afterwards.

Syntax

PROCEDURE StartAttached* (CONST program: ARRAY OF CHAR; arguments: Strings.StringArray): Process

Processes.Run

The common case in one call: start a program, let it say everything it has to say, and wait for it. FALSE when it could not be started at all; a program that ran and failed returns TRUE with its exit code, because that is a thing it did and not a thing that went wrong here.

Syntax

PROCEDURE Run* (CONST program: ARRAY OF CHAR; arguments: Strings.StringArray; VAR output: Strings.String; VAR exitCode: SIGNED32): BOOLEAN

Processes.Environment

What the environment says a name means, as the program was started with it. FALSE when it says nothing, which is not the same as saying nothing at all: an empty value is still a value.

Syntax

PROCEDURE Environment* (CONST name: ARRAY OF CHAR; VAR value: ARRAY OF CHAR): BOOLEAN

Processes.Id

This process's own identifier, as the system that started it knows it. What a program needs it for is a name nothing else will pick -- a socket, a scratch file -- and asking the host for it directly is what made programs import Unix and stop building on Windows.

Syntax
